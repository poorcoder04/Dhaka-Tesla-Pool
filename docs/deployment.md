# Deployment

How to deploy Dhaka Tesla Pool to Render with an external Postgres, and what
to check afterwards.

The target is **Render (free tier) + Neon (free tier Postgres)**. The
Blueprint is [`render.yaml`](../render.yaml) at the repo root.

## Why not deploy the compose file as-is

`docker-compose.yml` defines four services including its own Postgres. A
platform deploys **one service per deployment** — it builds a single image
from a single Dockerfile and runs that one container. There is no way to
hand Render the compose file. So deployment is not configuration; it is
splitting the one local stack into two independently deployable services
and moving the database off-platform.

| Locally | Deployed |
| --- | --- |
| `postgres` service | Neon (external, free tier) |
| `prisma_runner` one-shot job | migrations run from your machine, once |
| `backend` service | `dhaka-tesla-pool-api` web service |
| `frontend` service | `dhaka-tesla-pool-web` web service |

## Why Neon and not Render Postgres

Render's free Postgres **expires after 30 days**. If the deployment is
supposed to still be working when someone opens the link weeks from now, a
database that deletes itself is not a deployment. Neon's free tier is
permanent. Supabase works equally well.

## Before you start

Two accounts, both free, no card required:

- **Neon** — console.neon.tech
- **Render** — dashboard.render.com

Generate the database, then copy its connection string. It looks like:

```
postgresql://user:password@ep-xxx.region.aws.neon.tech/neondb?sslmode=require
```

Keep the `?sslmode=require` parameter. Neon requires TLS and the app's `pg`
driver reads that parameter directly.

## Step 1 — Create the database

In Neon: create a project, then a database. Copy the connection string.

Verify it locally before deploying anything, so a database problem is never
mistaken for a deployment problem:

```bash
cd backend
$env:DATABASE_URL="postgresql://...neon.tech/neondb?sslmode=require"
npx prisma migrate deploy     # create the schema
npx prisma db seed           # zones + the four demo accounts
npx prisma studio            # look at it, then close
```

`migrate deploy` applies the existing migrations. It does not create new
ones — those are made with `migrate dev` during development. Seeding is
idempotent, so re-running it is safe.

## Step 2 — Deploy the backend

Render → **New → Blueprint**, and point it at this repository. Render finds
`render.yaml` and shows both services.

**Deploy only the backend first.** Create `dhaka-tesla-pool-api` alone and
fill in the two prompted values:

| Variable | Value |
| --- | --- |
| `DATABASE_URL` | the Neon connection string from Step 1 |
| `FRONTEND_ORIGIN` | leave a placeholder for now, e.g. `http://localhost:3000` |

`JWT_SECRET` is generated by Render as a 256-bit value and is preserved
across later Blueprint syncs. Do not replace it with the value from
`.env.example` — that one is public in the repository history, and anyone
holding it can mint a valid token for any account including a driver's.

When it finishes deploying, note the URL, e.g.
`https://dhaka-tesla-pool-api.onrender.com`. Check it:

```bash
curl https://dhaka-tesla-pool-api.onrender.com/health
# {"status":"ok","timestamp":"..."}
```

## Step 3 — Deploy the frontend

Create `dhaka-tesla-pool-web` and set the one prompted value:

| Variable | Value |
| --- | --- |
| `NEXT_PUBLIC_API_URL` | the backend URL from Step 2, no trailing slash |

This is read at **build** time. Render passes it into the image build as a
Docker build argument, so `next build` freezes it into the client bundle.
Note the frontend's URL, e.g. `https://dhaka-tesla-pool-web.onrender.com`.

## Step 4 — Point the backend's CORS at the frontend

Set on the **backend** service:

| Variable | Value |
| --- | --- |
| `FRONTEND_ORIGIN` | the frontend URL from Step 3, no trailing slash |

Then trigger a redeploy of the backend. The browser calls the API
cross-origin, so until this matches, every request is rejected by CORS.

**This is the step that produces a blank page that looks like a broken
deploy.** The app loads and the panels never fill. If you see that, this
value is the first thing to check — an extra trailing slash is enough to
break it.

The order is deliberate and cannot be collapsed into one pass: the frontend
needs the backend's URL at build time, and the backend needs the frontend's
origin. Each has to exist first.

## Step 5 — Verify against the deployed stack

Local testing cannot catch any of the following, so do it here:

1. **Open the deployed frontend.** Not `localhost` — the deployed URL.
2. **Sign in as Jashim** (`01700000001` / `DhakaPoolDemo123!`), the driver.
3. **Sign in as Nusrat** in a private window, and request a ride Banani →
   Mohakhali.
4. **As the driver, accept it.** Then Rafiq and Shirin join until the pool
   is full, then a fourth passenger is refused.
5. **Run the lifecycle:** arrive → start → complete. Confirm the wallet is
   debited and the fare shows the pooled discount.
6. **Open the browser console.** Any CORS error here is a `FRONTEND_ORIGIN`
   mismatch.
7. **Cancel a ride** and confirm the seat returns to the pool.

Then check the things a first deploy gets wrong quietly:

```bash
# Is the API URL really baked into the bundle, or still localhost?
curl -s https://dhaka-tesla-pool-web.onrender.com | grep -o 'localhost:5000' || echo "no hardcoded localhost — good"
```

## Gotchas, in the order they bite

**Free-tier services sleep.** A free Render web service spins down after a
period of inactivity and the first request afterwards is slow while it wakes
— often 30–50 seconds. It is not broken. If a reviewer opens the link and
sees a long pause, that is why. Any request that wakes the service will
succeed.

**The frontend build is cached.** `NEXT_PUBLIC_API_URL` is frozen at build
time, so changing it and hitting *Restart service* changes nothing — the old
value is still in the bundle. Use **Manual Deploy → Clear build cache &
deploy**.

**Migrations do not run automatically.** Render's pre-deploy command is a
paid feature. On the free tier, re-run Step 1's commands whenever a migration
is added. A deploy that needs a new column will start and then fail on the
first query that touches it, which looks like an application bug.

**Neon pooled vs direct connection string.** Both work. The pooled
connection string (`-pooler.` in the hostname) goes through Neon PgBouncer
and is better for a free tier, since it survives many more concurrent
connections. The direct one is better for migrations. Using the pooled URL
for `migrate deploy` works but can be slow.

**`PORT` is not 5000.** Render assigns its own and routes traffic there. The
Blueprint deliberately does not set it. The backend reads `process.env.PORT`
with a 5000 default, so it follows whatever Render provides.

**Nothing secret is passed as a build argument.** Render converts every
environment variable into a Docker build argument, and a build argument
referenced in a Dockerfile can end up baked into the image. The backend
declares no `ARG` for its secrets, and both `.dockerignore` files exclude
`.env`, so `DATABASE_URL` and `JWT_SECRET` are runtime-only. If you add an
`ARG` to either Dockerfile, do not point it at a secret.

**Zero-downtime deploys are on.** Render starts the new instance, waits for
it to pass its health check, switches traffic, then sends `SIGTERM` to the
old one. The backend handles `SIGTERM` by closing the Prisma pool before
exiting, so in-flight requests are not cut off mid-transaction.

## Rolling back

Render → the service → **Deploys** → pick a previous successful deploy →
**Rollback**. It redeploys that commit. If a rollback lands you on a commit
whose migrations are not yet applied, run `npx prisma migrate deploy` against
the database. Migrations are forward-only; there is no automatic down.

## What is not covered by this setup

- **No autoscaling.** Free tier runs one instance. The backend is stateless
  so more instances would work, but the rate limiter's counters are
  in-memory and would stop being global — see
  [`architecture.md`](./architecture.md).
- **No PgBouncer of our own.** Neon provides one on the pooled connection
  string, which is why the deployment can exceed the 10-connections-per-
  process default that `pg` would otherwise impose.
- **TLS is terminated at the platform.** The app serves plain HTTP and
  relies on Render's certificate. `trust proxy` is set to 1 hop so
  `X-Forwarded-For` is read correctly, which the rate limiter depends on.
